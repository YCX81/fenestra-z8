## 追加针对性验证：真实来源已定位

新增 probe 只修改原 driver 的一个点位字典；固件、输入、deadline、恢复断言和 runtime offsets 不变。除了所要求的等待点，还覆盖 18 个同层 `0x80` / `0x100` 条件失败分支，因而抓到真正来源。driver SHA-256 `e9c15f2eb268f33805a41b301c17eef58880f7f0ccae021001c86cf183b5de5e`；plugin ring 21,274 条、覆盖 0、寄存器读取错误 0。完整原始 ring 已保存。

关键时序（全部在 step-114 之后、step-115 之前，REC step-116 尚未发生）：

| ring seq | 观测 |
|---|---|
| 19089–19091 | `41152044/41152094` 收到事件 `41020402`、pending `3`，随后 `411520c0` 置 OS event `0x1000` |
| 19092 | **`4115fbe4` 失败分支命中**，LR `4115fbc0`，日志标签 `w1=0x30b6` |
| 19093 | `40f5b2a0` 收到 **status `0x100`**，LR **`40f55b60`** |
| 19094 | `40f532bc` 调用者 LR `40f4b600`，确认来自前述事件转换入口 |
| 19095–19096 | kind `0x40` → history `A2` |
| 19097–19098 | 此后才进入 `41154db8(mode=0)` → `41155310` |
| 19099–19101 | 完成通知 pending `3` 再次置 `0x1000` |

| 19134 | `41154db8` 最终返回 0 |

三次 `41155434` 等待全成功；`4115545c` 从未命中。所增 18 个其他条件失败点中，仅 `4115fbe4` 命中一次。因此该次 A2 不是“等待 0x1000 失败”。

真实分支的静态路径为：

```text
40f55b58 -> 4115f6bc -> 4115f858 -> 4115faf8
  -> 4115fbbc 等待失败 -> 4115fbe4 result |= 0x100
  -> 返回 40f55b5c -> 40f5b2a0(status=0x100)
  -> 40f4b0a8 -> 40f532bc -> capture kind0x40 -> A2
```

`4115faf8` 清除同一 OS event 对象 `0xa0496efe0` 的 `0x40040` 和 `0x1000` 位，依据字节 `0xa0496f4e8` 选择命令 `0x3049` / `0x304a`，调用 `41169330(0)` 与 `41169330(1)`，然后在 **`4115fbbc`** 调 `40d2be54`，超时参数仍为 **`0x96`**，等待掩码是该字节为零时 **`0x40`**、非零时 **`0x40040`**。返回 bit0 为零才会到达已实测的 `4115fbe4`。

这已实证“该事件等待的包装返回为失败，形成 status 0x100 再分类 A2”。本轮 probe 没有直接采集 `4115fbbc` 的参数、该模式字节或底层原始 RTOS 返回码，因此尚不能区分两种 mask，也不应将所有非零 RTOS 错误都直接称为 timeout。最后一条成功的 `0x1000` 通知与真实等待的 `0x40/0x40040` 是不同位，不能互相替代。

本轮继续完整原断言：事务 1、事务/流错误 0、编码 413 帧、REC 预览 37 帧且预览错误 0；返回后 IRQ 1588、编码 413 不增长，仍报 `No new Live frames/encoding after half-press return`。run 退出 1，自有 QEMU 已停止，输入文件未变化。新 MOV SHA-256 `d19c2d9cc4efeda5006d928bc997e36faee2263c37b129f20750c2f59bbafd1a`。

## 原厂上游分类与具体条件

`40f532bc` 处理包 `{u32 kind; u8 flag @4; u32 mask @8}`；通过全局模式允许的 mask 检查后，在 `40f5338c` 调用 `40ece93c`。已有 probe 的 LR `40f53390` 只证明到了这一层，不保留其调用者。

有一条静态可达的事件转换链：

1. `40f4b0a8` 接收事件 `0x04190181`，从 payload 首个 u32 取索引。
2. 表 `0xa029d8770` 每项 12 字节；索引 9 内容是 `[0x40, 0, 0x10]`。转换结果为 kind `0x40`、flag `0`、mask `0x10`，随后在 `40f4b5fc` 送入 `40f532bc`。
3. `40f5b2a0` 将输入 `w0=status` 分类。`40f5b35c..370` 的精确条件为：

   ```c
   if (status & 0x400) code = 14;
   else if (status & 0x800) code = 16;
   else if (status & 0x180) code = 9;
   else if (status & 0x20) code = 8;
   else code = 15;
   ```

   非零 status 在 `40f5b3bc..3c8` 通过已注册回调发送 `event=0x04190181`、`payload[0]=code`、`payload[2]=status`。因此这条路径上，`(status & 0xc00)==0 && (status & 0x180)!=0` 会产生 A2。
4. `40f5b228` 根据状态字节 `0xa03bbbb92` 和目标状态调用启动函数 `41154124` 或停止函数 `41154db8`，随后将返回掩码传给 `40f5b2a0`。启动路径的调用后 LR 是 `40f5b25c`，停止路径的调用后 LR 是 `40f5b28c`。

A2 因此不是已能唯一解释为某一个硬件故障的编号；状态 `0x80` 和 `0x100` 都可以被归到这一类，且捕获包处理函数还有其他静态调用者。另有 `capseq` 调试命令注入表，但本驱动没有调用该命令，不把调试路径当作本轮来源。

## 已找到的具体等待失败候选

停止函数 `41154db8` 的 mode 为 0 或 3 时，会先调用 `41155310`，保存并最终 OR 合并其返回掩码。

`41155310` 在 `4115541c` 提交下层命令 `0x21` 后，执行：

| 地址 | 可证明动作 |
|---|---|
| `41155424..34` | `40d2be54(event_object=0xa0496efe0, mask=0x1000, out=&stack_word, timeout=0x96)` |
| `40d2be54..98` | 从对象取 event ID，调用 `4017c040`；底层返回 0 时包装函数返回 1，否则返回 0 |
| `41155438` | 返回 bit 0 为 1 时跳过失败分支 |
| `4115545c` | 失败时 `result |= 0x100`，并在 `41155460` 写原厂日志标签 `0x3110` |
| `411554b4..c8` | 返回该掩码，最终并入停止函数返回值 |

这里确实是一个带 `0x96` 超时参数的事件等待失败；尚未核定这个参数的物理时间单位，不直接写成毫秒。包装函数将所有底层非零返回统一映射为失败，所以仅从此分支也不能再区分超时与其他 RTOS wait 错误。

对应的一个置位来源已经找到：`41152044` 的事件分派表 `0xa02a980f0` 将事件 `0x41020402`、`0x41020404` 送到 `41152094`；它检查输入参数 `x1` 的 bit 0，为 1 时在 `411520c0` 对同一对象置位 `0x1000`。尚未将这些事件名或输入 bit 0 可靠对应到具体传感器/硬件完成语义。

因此能提出的精确候选是：**停止子流程提交命令 0x21 后，等待 event 对象 0xa0496efe0 的 0x1000 位失败，返回状态增加 0x100，随后可能分类为 A2。** 不能把这个静态候选写成已经发生的运行事实。扫描还发现多处其他 `0x80` / `0x100` 状态产生点，不能只凭最终 A2 排除它们。

## 初次静态追踪提出的最小观测（现已执行，见开头）

不需要修改返回值、固件 deadline 或屏蔽错误；使用已有只读 plugin 点即可。

- `40f5b2a0`：记录 `w0=status` 和 LR。先区分启动/停止返回，确认是否是 `0x80`、`0x100` 或组合。
- `40f532bc`：记录 LR；补齐错误包是从事件转换还是其他入口产生。
- 若确认上述停止路径：`41155438` 记录等待包装返回值；`4115545c` 是否命中判定该具体失败分支；必要时 `40d2be80` 记录底层原始返回码。
- `41152044`：记录事件号与 `x1`，区分对应完成通知未到达、参数 bit 0 未置位、或通知/等待的顺序问题。只记录这个入口仍不能单独证明硬件模型根因。

初次静态追踪止于上述证据边界。其后按明确要求执行的针对性验证见开头，结果完整保留失败，没有删除断言。

## 文件与版本一致性

`error-static-provenance.json` 核对以上 8 段相关代码在原版 v49、合并 v50 和 v51d 中逐段 SHA-256 完全相同。这证明这些原厂分支未被本次 patch 改写；并不证明固件其他改动无法改变调用时序。

静态证据：`error-producer-disasm.txt`、`error-upstream-disasm.txt`、`error-status-disasm.txt`、`error-wait-event-disasm.txt`；运行证据：`qemu-v51d-stock-error.json`、`recovery-failure-evidence/v51d-final-pb-recovery/`。

结合 v50 同一版本已有两次完整恢复通过和两次失败、v49 菜单阶段也出现相同 kind/A2，本轮不能归因于新 writer；这些对照同样没有证明模型是唯一根因。实验包应继续保持 `core_regression_passed=false`。
