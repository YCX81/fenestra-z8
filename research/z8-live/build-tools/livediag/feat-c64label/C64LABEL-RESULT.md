# C64 共享标签 28 号最小补丁

已在 `bg34.main` 上离线应用。只改275个字节，不加代码、不扩字框、不加PNG。原始 MAIN 与已有 FIX1/PLAN 文档保持原样。没有连接USB、刷写、操作相机或运行QEMU。QEMU步骤见 [C64LABEL-QEMU.md](C64LABEL-QEMU.md)，尚无候选的动态画面结论。

- [独立完整diff验证](evidence/c64label-verification.json)、[验证脚本](verify_c64label.py)、[本次反汇编证据](evidence/c64label-disassembly.txt)。

```

```

复现命令（输出名必须不存在）：


## 补丁位置与字节证据

编号 `i=0..274`，槽位 `10+i//5`、variant `i%5`，资源ID `0x7e00+i`。

| 项目 | 确切地址公式 |
|---|---|
| MAIN描述符首址 | `0x40b37208 + 0x20*i` |
| MAIN style字段/改动字节 | `0x40b37214 + 0x20*i` |
| 文件offset | `0x009d7214 + 0x20*i` |
| 运行时描述符 | `0xa116d0200 + 0x20*i` |
| 运行时style字段 | `0xa116d020c + 0x20*i` |
| 原style小端u32 → 新style | `1f 02 00 00` → `29 02 00 00` |

因此每项只改低字节 **0x1f → 0x29**。首项为 `0x40b37214`（C10/v0/ID7e00），末项为 `0x40b39454`（C64/v4/ID7f12）。完整逐字节清单已链接在上面，不省略中间项。

这是**初始化数据源**，不是直接拿RAM VA减MAIN基址：启动代码 `0x40b20058..c4` 从 `0x40b20200` 读稀疏段表、从 `0x40b20608` 顺序复制数据到 `0xa1162b000+段offset`。其中 offset `0xa5200`、长度 `0x2250` 的段来自MAIN `0x40b37208`，包含全部275项的有效描述符字段。段尾到 `0x40b39458`，初始化数据总结束 `0x40b39460`。

解析入口 `0x4032e70c → 0x40b12400` 对范围内ID减0x7e00，按 `index<<5` 加到 `0xa116d0200`；`0x40b12428` 读描述符+0xc，`0x40b12444` 返回style。原厂ID落回 `0x4032e710`，所以C1..C9资源不受这275字节影响。原厂样式表本身也未改。

`0x229 @0x43a0f7d0` 为 `12 1c 02 64 00 00 00 00 ff 00 00 00 00 00 00 00`；原0x21f仅第二字节为0x24。`0x4032b884..88c` 将该尺寸写入渲染记录的宽/高字号字段。脸号均0x12，尺寸36→28。

## 62宽评估

**普通 `C-10`..`C-64`：预计可以放下，约56宽；这是有依据的估算，尚不是原厂测宽函数或QEMU像素实测。带ASCII星号的5字符形式按同一估算约70宽，有越界风险。**

依据和限度：

1. 四套state2文字矩形都是62×28（原审计 `evidence/static-audit.json`），原厂 `C-1`..`C-9` 使用0x229；真机照片 `evidence/img_5008.jpg` 可见 `C-5`..`C-9`。原厂字号28与矩形高度28吻合。
2. 本次进一步追到实际字体资源：`0x403ee410..420` 将指针表 `0x42dec310` 注册；`0x4032dfbc..d4` 按style首字节索引。脸号0x12指向 **0x42dbf97d，10591字节，`hif\x01`格式**。原始表和头部见 [width-and-refs JSON](evidence/c64label-width-and-refs.json)。它不是TTF，也不能用桌面字体的宽度充当原厂宽度。
3. 该HIF头 `+0x18=0x0400`、`+0x1a=0x0800`；结合图中约42宽的三字符原厂标签，支持ASCII约半em的估算：`28/2=14`，四字符56，留6宽；五字符70。**本次未完整解码HIF advance表/原厂layout取整与字距，因此没有把这两个头字段单独宣称为已证明的字宽ABI。** 真机拍摄图有透视与屏幕缩放，约42也是估计值。
4. 无星号的55种两位数标签在半em估算下相同；优先验证 `C-10`/`C-11`，同时建议补 `C-64`/`C-58`，防止实际存在比例字宽/字距差异。不能从“高度28”单独推出“宽度必然≤62”。

**当前扩展带星号形式不存在**：静态解包275项，length全部为4，五种variant全部是对应 `C-xx`，没有 `*`；state2扩展分支跳过原厂添加星号的格式化。C1..C9原厂可以构造星号版本，但不在本次改动范围。将来若恢复 `C-10*` 或 `*C-10`，应独立测宽；若使用Unicode星形，也不能套用ASCII五格的估算。

若实测普通形式仍裁切，最便宜的备选是去连字符成为 `C10`（约42）；若未来需要星号，`C10*`（约56）比 `C-10*` 稳妥。**这些备选均未实施**，本候选严格只改style字段。

## 与其他补丁的地址关系、diff结论

改动集合完全包含在 `[0x40b37214,0x40b39455)`；这是集合的包络，实际仍只有275个单字节。

- bootguard cave：检查 `[0x401fe000,0x40200000)`，逐字节相同；六个已知补丁点 `0x401c4d4c / 0x401c4d58 / 0x401c4d7c / 0x401cf98c / 0x401d8960 / 0x401d8984` 各4字节相同，build-id也不改。各范围SHA见changed JSON。
- Live payload：`[0x401e2000,0x401fff80)` 整段相同。
- NFP查表/重映射：`[0x40a41000,0x40a42000)` 相同；入口钩子与所有PNG资源也由全文件diff保证未改。
- 不是只抽查上述区间：独立比较两个81,807,709字节文件，差异offset集合**严格等于** `{0x9d7214+32*i | 0≤i<275}`，每项严格为1f→29，全部275个u32分别为21f→229。因此任何上述区间之外的bootguard/NFP hook也没有被此补丁改写。

这些是文件字节及地址无重叠结论；共享控件变小是明确接受的功能影响，尚需实验室截图验收，未据此给出刷写结论。
