## 调查结论

**首要根因假设是 Live Photo 与原厂录像之间的 Wave5 交接未完成。已证的代码缺口是关闭失败后，原厂仍可继续启动。** v31 在切档过程中主动关闭编码器。后续版本允许进入录像待机，却可能在按下 REC 后遇到同一个核心仍被占用、服务只关闭了一部分，或原厂重新初始化失败。故障当次缺少最后执行位置、任务栈和复位原因，仍不能唯一确定哪一步先停住。[真机 A–F 对照](PROMPT8.md) · [原厂错误传播](history/astra-bbzen9eh9.md)

### 现有记录器能回答什么

- v2 两次复现生成的文件均为 2048 B，仅第一个扇区有有效的准备事件 0，后三个扇区全零。run1 SHA-256 为 `918a282a2460018bdb1840c54203a6d36994b634998e25cc6ec04f0ba6629062`。实验电脑归档的 run2 为 `c700a1aac9d2b0fdcf37168e620fa7d0fc32373ea834ea56d30f20dc082454b4`。两次都没有保存故障时的服务返回值。录像待机读到的 `ff ff ff ff 00` 表示 Live client 4 仍占 stream 0。[run1 原件](../feat-rec/linked-recorder/W5F00001-run1.BIN) · [v2 事件定义](../feat-rec/recorder-owner/recorder/README.md) · [录像待机 RAM](snap3/r2.json)
- v2 可以在照片档通过 USB 单独开启记录器，确认新编号文件已准备好，再拔线复现。该操作与写 `release_req` 或手动关闭 Wave5 各自独立。事件 2 只有在事件 1 建立身份、门控通过且同步写卡成功时才可能留存。后续 v3b 真机 run3（MAIN `0001bbd3…`）在交还前保存了事件 15，取得 `client=0, LR=0x40d07ba8`。记录中仍缺 REC 的服务返回值。未武装对照同样重启。[v2 武装程序](../feat-rec/recorder-owner/recorder/arm.py) · [v3b 原始记录](../feat-rec/runs/W5F00003-run3.BIN) · [v3b 故障条件](../feat-rec/ANALYZE2.md#L2)
- **最小故障诊断设计**是在同一次 REC 的两处取样。`0x402f303c` 读服务原始 `W0`、请求 client `W19`、候选 slot 和绑定前映射。`0x402f3068` 在成功、失败分支汇合后读同一 client 的映射。前一点读到 `rc=0、map=ff` 可以是正常现象。若要证明 adapter 实际拿 `ff` 去 OPEN，直接证据在 `0x402f4620`。曾提出用带阶段号和校验的卡灯短码独立输出，未实施。灯和原厂共用，缺码不能定位故障。[原厂绑定和 OPEN 路径](history/astra-bbzen9eh9.md) · [GPIO 标记](../v34_patch.py)

### 机内归还编码器的时机

**设计判据**是收到录像请求后先冻结新帧，同一次切换的照片图像支路成功停稳后，保持旧缓冲有效并让 Wave5 worker 继续运行，执行已验证的排空流程。只有 FINISH 后 worker 为 0、实例已释放，且 EXIT 已返回、服务和映射确已归还，才允许新的录像或回放使用者启动。若关闭失败，仍被引用的缓冲应由 Live 保留，新请求需要能返回失败。[主机关闭的终态检查](../w5seq.py) · [原厂会话收尾顺序](history/astra-bswpcsmbw.md)

**2026-11-10 QEMU 实跑补证。** v3b 活动取景拨档时，ch1 停止应答 `0x40e91078`（序号 27）早于布局转换 `0x40f7a4bc`（29），按 REC 后才有首个非 Live client 0（37）。三个点均读到 Live 占有 stream 0。应答至布局入口之间已有描述符释放调用，尚未证明相关 Live 缓冲可安全排空。REC 抢占后已走完 Live 退出调用并进入原厂板级启动，QEMU 模型拒绝了其间两笔复位写。真机死机时的板级状态、REC 的服务返回值及最后映射仍未知。后文对话按原貌保留。[本轮时序、停止边界和离线重放对照](qemu-handoff-20261110/README.md) · [逐条探针](qemu-handoff-20261110/trace04-timeline.tsv)

**NR 模型修正后的 v3b 结果。** 旧模型把已写入 RAM、等待解码的前端包计入全局忙状态，因而拒绝两个空 NR 端口复位。补模后同一固件在第 5 包仍待解码时通过了两次置位和解除复位，包随后被正常消费。同一次首次 REC 的 client 0 收到 `ack 2`，服务返回 `S=0`，绑定 stream 0，实际调用 `OPEN(0)` 并返回 0。真机故障当次仍只确认到 REC 入口。[修模实验和跨过拒绝点的实测值](qemu-nr-rec-20261110/README.md)

**继续追过 OPEN。** v3b 的原厂录像创建了实例，提交首帧，处理 INTID 120，并通过回调交回 HEVC IDR。在带声配置下未供给模拟 PCM 时，writer 为音频等了 60 次，卡上的 MOV 没有媒体轨；同一固件只增加已就绪的麦克风 DMA 输入，就写入了 12 帧 HEVC 和双声道 PCM，卡中第一帧的 IDR 与本次编码回调一致。[对照与原厂 MOV](qemu-rec-after-open-20261110/README.md)

##### 为什么 v31 拨档就会死

**【源码与反汇编已证】** v31 的 Live 工作线程读取 `0xa03bd062c`。这是原厂拍摄状态机更新的模式值。只要它变为非照片状态、Live 没有正在封装的文件任务、编码器对象存在，线程就调用 `live_encoder_release()`。这些检查能说明 Live 可以停止生产照片帧，却没有检查原厂取景、编码服务或相关硬件是否已到允许断电的时刻。[v31 工作线程](src-fix31/runtime.c#L211) · [MAIN 镜像，模式值写入点 `0x40fde01c`](bg34.main)

`EXIT(4)` 也不只是归还一个软件句柄。原厂先在 `0x402f3094` 关闭服务，再在 `0x402f30b4` 清 client 映射，随后才操作板级复位、时钟和电源。即使服务关闭报错，代码记录错误后仍进入板级序列。与此同时，另一个原厂调用者若进入 Live 钩子，`live_encoder_preempt()` 会先检查 `alive()`；一旦映射、slot 或 VDI 已清，它可以在检查 `busy` 或等待关闭锁之前返回。实际 MAIN 中，外围六个貌似负责加锁、解锁的入口都是 `RET`，没有把整段退出和重新上电串行化。[v31 的提前返回](src-fix31/codec/live_w5enc.c#L320) · [EXIT 指令顺序](history/astra-bfz5f70qd.md#L26) · [外围函数核验](history/astra-bptes20qq.md#L60)

**【推断】** v31 最值得怀疑的窗口，是 Live 已经从软件表中消失，硬件退出却尚未结束。此时原厂可以开始重新上电，Live 工作线程仍可能继续复位或关时钟。原厂正常结束录像前会先收尾自己的 adapter、异步回调和缓冲绑定；Live 只依据模式值发起关闭，缺少这层保证。历史记录里有靠近切档的 client 2 调用，但没有 v31 故障当次的调用轨迹，所以能确认这个竞态可达，不能确认当次就是这两个调用相撞。v32 删除工作线程关闭之后，这个具体竞态也不足以解释后来的 REC 故障。[原厂收尾顺序](history/astra-bswpcsmbw.md#L46) · [v31 现场证据边界](PROMPT4.md#L3)

##### 为什么后来能切到录像档，一按 REC 仍会死

**【真机读数已证】** 我重新比较了照片档 `r1` 和录像档 `r2` 的 RAM 快照。模式值已从 0 变为 1，但两边都是 `svc_up=1`、VDI 为 `0x16010000`、slot 0 已用、核心 A 忙、client 映射为 `ff ff ff ff 00`。最后一个字节表示 Live 的 client 4 仍持有 stream 0。也就是说，**屏幕已经进入录像待机，编码核心仍属于 Live**。照片模式下 Live 在按快门前就会持续编码，所以“这次没拍 Live 照片”和“本次开机从未运行 Live”是两个不同的对照。[照片档快照](snap3/r1.json#L2) · [录像档快照](snap3/r2.json#L2) · [未拍照仍在 REC 复现](PROMPT8.md#L7)

**【真机对照】** v29 曾经报告 `eos_ok=1`，实际 `fin_rc=0x01040400`，关闭前后 worker 都是运行态 4，VDI 也仍然开启。一次正常帧完成或 EOS 标志置位，不足以证明编码器已经排空。反过来，在 v25、v29 的 USB 对照中，主机完成了 STOP、最后一帧、第二次 drain trigger，等到 worker 进入 5，再 FINISH 到 worker 0、实例释放，最后 EXIT 到 VDI 0；拔线后原厂 REC 恢复，Live 的内存块当时仍保留。只在照片档预置 `release_req=1`、暂停送帧，拔线后仍会在 REC 失败。**这组正反对照，是把调查重点放在编码器交接上的最强证据。** USB 同时停止取景、改变执行上下文和时序，因此它没有单独证明脱线故障发生在哪一个关闭步骤。[v29 关闭读数与成功序列](history/hw-notes.md#L27) · [USB 对照条件](PROMPT8.md#L3)

**【反汇编已证】** 原厂 REC 有一条具体的错误传播路径。我在 `bg34.main` 和最新实测镜像中核对了关键调用点。

1. 录像任务 `MOVRS_F` 已安装录像缓冲，随后在 `0x40d07ba4` 调用 Wave5 bring-up。Live 的交接钩子在这里执行。如果发生关闭失败，Live 会记录 `close_failed`，钩子仍把控制权交回原厂。[录像任务调用顺序](history/astra-bswpcsmbw.md#L81) · [实测版交接代码](../feat-rec/recorder-owner/codec/live_w5enc.c#L379)
2. 服务层 `0x40c32fec` 可能因核心 A 仍忙或 slot 已满返回 `2`；若资源槽已释放，但服务仍使用 Live 的工作区，录像传入另一工作区，则可能返回 `4`；冷初始化握手超时还可能返回 `5`。这些路径都不会绑定新的录像 stream。**`0x40d07ba8` 随即覆盖返回寄存器，`0x40d07bac` 照常启动 adapter。** 这是两个镜像中都能确认的缺口。[服务分支与调用者指令](history/astra-bbzen9eh9.md#L24)
3. 如果录像映射仍为 `0xff`，adapter 的 OPEN 会把 255 当成 stream 索引。正常两把锁的 ID 是 `0x81/0x82`；错误索引算出的 `0xa02d30c4c` 实际落在 stream 0 参数区，在 Live 运行过的快照里首字为 `1`。它可能等待无关的信号量。如果等待返回，代码还会把回调指针写到合法回调表之外的 `0xa02d312c8`。与此同时，录像任务在 `0x402f58c8` 等待 adapter 完成事件，没有本地超时。**这解释了交接失败怎样演变成录像长期无响应。** 普通错误返回仍可能走到发送完成事件；要把这条路径认定为现场根因，还需要看到当次的 service 返回值、实际 stream 或阻塞任务。[无效 stream 指令链](history/astra-bbzen9eh9.md#L114) · [RAM 原始快照](snap/ran-svc.bin) · [RTOS 信号量接口](../../../Fenestra-upstream/host/platform_profiles.py#L96)

**用户**

**用户**

**助手**

之前有两种 USB 操作。成功记录里确实写过一个值：把 Live 的 `release_req` 置为 `1`，暂时不再送新帧。单独写这个值、在照片档拔线，后来按 REC 仍然重启。另两次成功是在录像档接着 USB，由电脑把最后一帧排空、释放编码实例，读到 VDI 已归零，再拔线按 REC。我在核对那次“只记得写了一个值”的运行，它中途还在录像档重新接过 USB，不能直接归因给这个值。

**助手 · 进度**

第二次复现也查到了。读回的 `W5F00002` 原件同样只有准备扇区，后面三个扇区全零。还有一个影响判断的细节：现有记录器在 `0x402f303c` 读映射时，原厂还没写入新 stream，所以即使在那里看到 `ff`，也要结合返回值和绑定后的映射来解释。

**助手**

你记得的那个东西，很可能是电脑经 USB 写进相机 RAM 的一个数：**`release_req = 1`**。它写在 Live 编码器对象的 `+0x24` 位置。程序随后连续读两次帧计数，确认 Live 已经停送新帧，也没有编码调用正在执行。[实际写入代码](../w5seq.py#L40)

**为什么后来按 REC 能成功，要分两次实验看。**

- **v31 那次，写 `1` 首先救了拨档。** 原来一拨到录像档，Live 工作线程就会在原厂切换取景的过程中自行关闭 Wave5。写 `1` 会让它跳过这次关闭，因此拨档能够完成。之后又在录像档重新接过 USB，拔线后 REC 成功。但当时调试读取失败，没有拍到是谁、在哪一刻归还了编码器。USB Debug 会暂停取景，这次重新连接改变了实验条件。[v31 实验 C](PROMPT8.md#L5)
- **v25、v29 成功的两次，电脑还做了完整的关闭。** 它让最后一帧完成，再触发一次排空，等到编码 worker 进入状态 `5`；随后执行 `FINISH`，读到 worker 回到 `0`、实例已释放；最后执行 `EXIT`，确认 VDI 和服务都已关闭。尤其关键的是，**v29 脚本在拔线按 REC 前，已经把 `release_req` 写回 `0`**。当时留给原厂录像的是一个已释放的编码器。[关闭与写回代码](../w5seq.py#L64) · [真机成功记录](history/hw-notes.md#L30)

### 现有记录器能不能拿到死机现场

还有一个决定性的时序问题：**事件 `2` 读到的是绑定前的映射。** `0x402f303c` 刚从服务分配器返回，成功分支要到 `0x402f3064` 才调用绑定函数。因此，即使事件 `2` 给出 `rc=0、map[client]=0xff`，也完全可能随后正常绑定到 stream 0 或 1。失败分支会跳过绑定。现有记录器不能保证一次同时取得原始返回值和这次绑定后的映射。[原厂绑定顺序](history/astra-bbzen9eh9.md#L12)

### 一次复现最有信息量的最小改动

我会保留原来的关闭流程和超时，只在**同一次 REC 的两个位置**取样。第一个位置复用已有探针，只新增第二个位置。

| 位置 | 记录什么 | 能回答什么 |
|---|---|---|
| `0x402f303c`，服务返回 | 原始 `W0`、请求 client `W19`、分配器输出字节 `[原SP+4]`、绑定前 `map[client]`。用原栈保存的 REC 调用者 `LR=0x40d07ba8` 识别此次调用，独立于事件 `1` 是否写卡成功。 | 服务是否返回、返回什么。输出字节初始为 0，失败时即使读到 0 或 1，也不能视为已分配。 |
| `0x402f3068`，成功与失败分支汇合 | 在恢复寄存器前，读取同一栈帧、同一 client 的 `map[client]`。 | `rc=2/4/5` 且映射仍为 `ff`，可确认本次服务失败且没有建立映射；`rc=0` 且映射变为 `0/1`，就应转查下游 adapter。若还要证明 OPEN **实际使用**了 `ff`，其直接观测点是 `0x402f4620`。[adapter 读取路径](history/astra-bbzen9eh9.md#L114) |

这两个点各发一段带阶段号和校验的短灯码，用手机连续拍卡灯；诊断模式跳过 REC 任务里的同步文件写入。这样即使只拍到第一段，仍能保住原始返回值。先在未运行 Live 的正常录像上验证两段都可读，再做一次脱线故障复现。卡灯与原厂共用，发码也会改变时序，所以**有效灯码能定分支，缺码仍不能定挂点**。这是一项诊断设计，本轮只读取了已有资料和电脑上的备份，没有连接相机或刷机。[已验证的 GPIO 139 标记](../v34_patch.py#L2) · [旧灯码的实测限制](history/astra-bkdhewcl4.md#L48)

##### 应该在哪个时机归还

我重新核对了 v31 的 `bg34.main` 和后来实测的 `ce1879c8`。下面几段相关原厂代码在两份镜像中相同。

1. **切档请求到达时，冻结 Live。** 原厂先根据属性 `0x218c` 更新 `0xa03bd0628`，再有条件地在 `0x40fde01c` 把值复制到 v31 轮询的 `0xa03bd062c`。更早的请求值适合用来禁止新一轮 Live 编码或重开实例。另有一条布局切换路径在 `0x40f7a4b0` 发通知、随后在 `0x40f7a4bc` 调用布局转换器；该通知本身也没有等待硬件停机。两者可以用来**开始冻结**，不能直接用来调用 EXIT。[模式与布局反汇编](bg34.main) · [布局通知调用点](../../../_mac-migration/files/_bundle-20261102/codex-tasks/live-ram/selector-callers-asm.txt#L257)
2. **照片支路返回成功的停止应答后，才考虑执行关闭。** 这是本轮找到的最有价值的候选边界。图像服务在 `0x40cb8ecc` 请求底层停止，`0x40cb8ee0` 等完成；另一条按活动通道收尾的路径，在 `0x40e91074` 等待本次请求的事件掩码，**`0x40e91078` 是能读到等待结果的位置**。要一起核对实际通道、等待是否成功以及回调状态：回调会先发事件再检查错误，而外层 `0x40e90d38` 最后甚至固定返回 `1`。只看“函数返回了”会把超时或失败也算成停稳。这里适合**观察和发出交接请求**；执行 STOP／drain 的任务还必须让图像服务和 Wave5 worker 能继续处理完成事件。[图像服务停止与完成](../../../_mac-migration/files/_bundle-20261102/codex-tasks/live-blackout/pipeline-low.txt#L386) · [按通道等待的位置](../../../_mac-migration/files/_bundle-20261102/codex-tasks/live-blackout/pipeline-stop.txt#L249) · [回调先发事件再查状态](../../../_mac-migration/files/_bundle-20261102/codex-tasks/live-b1-lease/rotation-initial-asm.txt#L373)
