# Wave5 硬件解码播放 Live MOV —— 调研（2026-11-13）

目标：机内回放 Live 照片时直接播放 MOV，画质、帧率与录像回放一致，取代现在的 15 fps JPEG 预览（LVP）。

## 结论

**推荐路线：整套复用原厂电影播放器（MOVS），不自己当 Wave5 解码客户端。**
原厂播放器已包含 MOV 解析、Wave5 解码、显示平面、喇叭输出和音画同步，画质帧率天然与录像回放一致。
自建解码客户端要补齐解码 ABI、DPB、显示 surface、音频时钟，现有资料里解码 ABI 一条都没有闭合，工作量最大。

当前状态（11-13 下午）：**原厂播放器只接受原厂分辨率（8K/4K/1920×1088 编码）**。1024×682 的 Live 片段真机沙漏；换成 1080p 的同容器片段在 QEMU 里已走到解码出画面，真机显示待测。详见“真机结果与后续 QEMU 追查”。

## 本次新确认的事实

1. 真机 Live 片段 `hw-DSC_0028.MOV`（v43 真机，hvc1 1024×682，95 帧）的 VPS/SPS/hvcC 均为 High tier、Level 4.0，`hvcC[1]=0x21`，满足固件 `0x40ce84ec` 的单字节检查。
2. 用 C3.11 固件自己的解析代码实跑（`parse_hw.py`，qemu virt 里执行真实指令）：
   - 现行 Apple 封装：`0x40ce8a08` 返回 6（拒绝）。
   - 相机格式（加 `niko` 品牌、去掉 mebx 轨、音频 co64→stco，mdat 不变）：返回 0，`0x40ce8470` 取出 VPS 33 B / SPS 416 B / PPS 7 B。
   此前同类验证只用过合成码流；真机 SPS 带 scaling list（416 B），这次是第一次用真机码流通过。
3. `0x40cf3ffc` 的 0x48 字节参数是显示/音频设置（调用点 `0x4071aff0` 逐项从设置读出），不含文件。`0x40cf5028` 是资源规划查询。**按路径播放的入口仍未找到。**
   电影回放 UI 层在 `0x40711000–0x4071d000`，经 `0x40cf4034–0x40cf4264` 约 35 个跳板调用 MOVS 服务。
4. 我们的 QEMU（merged）没有解码模型。上游 rdwing 树（win-lab `~/Nikon/rdwing-z8-qemu`）有 `nikon-wave5-decode.h`（libavcodec 主机解码）和原厂回放流程，但要 QEMU 11.1.1 源码和 ffmpeg 开发库，尚未构建。

## 沿用的既有结论（11-09/10，feat-mov）

- MOVS 启动链：`0x40cfc820 → 0x40cf9810 → 0x402f2d58`（Wave5 bring-up，已被 Live 的交接钩子接管）`→ 0x40cf9258`。MOVS 用 client 2/3，Live 编码用 client 4，争用同一个核。
- DCF 扫描：同目录同编号、不同前缀的文件会被跳过，测试文件必须用未占用的编号。
- NCDT（Nikon 元数据和缩略图）：解析器不强制，UI 列表/缩略图是否需要未知。
- 旧真机对照（AVC + Apple 封装）：冷启动未开 Live 时显示“不能显示此文件”；开过 Live 后直接重启。该次早于 v9b 的 CAS 死循环修复，现版本未复测。

由此新增的结论：

1. **NCDT 是必需的。** 没有它，条目显示“不能显示此文件”。writer 必须自己生成 NCHD、NCTG（至少厂商/机型/版本和图像尺寸记录）、四张 JPEG（NCTH 160×120、NCVW、NCM1、NCM2）和空 NCDB。
2. **分块必须按 GOP。** `0x40344268` 解析成功后连续调用 12 个取参函数，最后一个 `0x40ce6c84` 对 9003 返回 6。它要求：stss 第二项减第一项等于 stsc 首项的每块样本数；stsc 多于一项时，块总数等于第二项的起始块号。Live 现在是一帧一块，所以被拒。真机片段关键帧固定每 15 帧（1,16,…,91），改成 `stsc=[(1,15,1),(7,5,1)]`、7 个块即可通过，mdat 不动（`gop_chunks.py`）。
3. **通过校验后的路径**：`0x403457a4` 取 HEVC 参数集成功（共 0x24c 字节）→ `0x40cf9810` → Wave5 bring-up 成功（服务返回 0）→ `0x40cf9258`。
4. **QEMU 里卡在创建解码器之前。** Live 片段被分到 Wave5 client 3（4K 对照是 client 2，bring-up 第二参数分别为 0x6b6c0 和 0x2bf20）。固件做完 INIT（命令 1、0x4000）后没有发 CREATE（命令 8），约 2 个虚拟秒后 EXIT 并重试，循环，屏幕一直是沙漏；模型没有任何拒绝或未建模访问。上游模型只验收过 4K 回放，这一步是固件对该格式的额外等待还是模型缺口，QEMU 里没有分清。**真机才能判定。**

## 真机结果与后续 QEMU 追查（2026-11-13 下午）

真机放卡 LIV_9004：能列出，按 OK 后**一直沙漏**，与 QEMU 一致。所以这是固件逻辑，不是模型缺口。之后在 QEMU 里用覆盖率差分（`z8cov.c`，对照片 vs Live 片段的指令级差异）逐层追到三个原因：

1. **每帧必须以 AUD 开头。** 读样本的循环 `0x40d00670` 要求每个画面的第一个 NAL 长度 ≤4 字节（即 AUD），否则报错 0x400；一个 GOP 分块内靠"长度 3、类型 35"的 NAL 切分画面。原厂录像每帧是 `AUD(46 01 10/30) + 一个切片`。Live 帧只有切片。`aud_samples.py` 给每帧补 AUD（mdat 重排，+7 字节/帧）→ `LIV_9005-aud.MOV`，固件随即走到 CREATE、INIT_SEQ。
2. **分辨率只能是原厂的几种。** 配置 `0x40cf9c48` 把分辨率档位（`0x40d02cb8`：8K=0、4K=1、1920×1080=2；HEVC 只有这三档有方案）交给 `0x402f3264` 选"资源方案"（表 `0x42a002d4`，每项 0x24 字节，含 Wave5 client、宽、高）。1024×682 不在表内 → 实测选中 8K 方案（client 3，7680×4320）。注册帧缓冲 `0x40c347fc` 要求方案宽高与解码器报告的图像宽高**完全相等**，不等返回 4 → 适配器失败 → MOVS 等待超时、EXIT、重试 → 沙漏。真机同样如此。
3. **编码高度按 16 对齐。** 适配器传 `(高+15)&~15`，与解码器报告的编码高度比较。1080p 必须是编码 1920×1088（原厂如此）。

验证：把同一段 Live 画面转成 1920×1088 编码（x265，GOP 15，无 B 帧，AUD，High tier L4.0），套进同一个 Live 容器（`replace_video.py`）→ `LIV_9007.MOV`。QEMU 里原厂固件选中 1080p 方案，注册帧缓冲成功（5 次 DEC_FB），解码出第 1 帧，随后停在未建模的显示寄存器 `0x15421104`（上游模型只做了 4K 的显示路径）。即：**Live 容器 + 原厂尺寸，固件侧已走通到解码**；显示和音画同步只能真机看。

QEMU 模型的两处缺口（已在 win-lab 本地构建里修补，`~/fxfix/w5dec/rdw-model-local.patch`）：只接受 yuv420p（Live 是全范围 yuvj420p）；序列信息报告裁剪后的高度（真芯片报编码高度）。另加了 `Z8_W5_DUMP` 环境变量转储送入解码器的码流。带补丁固件运行用 `run_native_any.py`（绕过原厂固件校验）。

|---|---|---|
| LIV_9004 | 相机格式 + NCDT + GOP 分块 | 真机、QEMU 都沙漏（无 AUD） |
| LIV_9005 | 9004 + 每帧 AUD | 解码器创建并识别 1024×682，注册帧缓冲失败（选中 8K 方案），沙漏 |

## 路线判断

原厂播放器不能直接放 1024×682。两条路：

- **A. Live 改录原厂尺寸（1920×1088 编码）。** 固件侧不用补丁，QEMU 已验证到解码。代价：Live 源是 1024×682 的 LV 帧，需要放大或另取 1080p 源；3:2 画面进 16:9 帧要加黑边或裁切；码率和写卡量上升。
- **B. 给方案选择打补丁**：Live 片段选 1080p 方案并把方案宽高改成 1024×688。帧缓冲校验可过，但显示缩放是否按方案尺寸配置未知，QEMU 没有该显示路径的模型，只能真机迭代。

## 让播放器支持 1024×682（路线 B，2026-11-13 傍晚）

机制补充：
- 分辨率档位是**回放界面层**算的，早于播放器解析文件。界面层当前文件信息在 `0xa045f08f8`：`+0xc` 宽、`+0xe` 高（u16）、`+0x10` 档位（未知尺寸 = 9，经 `0x40714020` 变成 0 = 8K）。`0x4071af20…` 把它装进 0x48 字节参数交给 `0x40cf3ffc`。
- 方案选择 `0x402f3264(config, dst)` 是方案表的唯一读取点，四个调用者：适配器配置 `0x402f3e38`（先，此时 MOVS 的片段信息 `0xa0319f270` 还是空的）、MOVS 查询（经跳板 `0x402f2d54`，LR `0x40cf99e4`）、`0x402f45c8`、`0x402f6bbc`（非回放）。
- 方案项 0x24 字节：编码(0 AVC/1 HEVC)、u16 位深 + u16 宽、高、帧率分子/分母、0xf…、1/2、码流缓冲字节数、1/2。
- 带 NFP 的固件里，该函数尾部的复制已被 NFP 改跳 `0x40a10000`（复制后按 NFP 设置改码流缓冲大小）；原厂是 `0x4127a900`。

补丁（`win-lab ~/fxfix/liveplay/liveplan.S`，144 字节，放在 `0x401fd000`，入口 `0x402f3264` 改成跳转）：HEVC、档位 0、调用者是上面两个回放调用点、界面层文件信息为 1024×682 时，复制自带方案 `(1, 0x04000008, 0x2aa, 30000, 1001, 0xf, 1, 0x2aea540, 1)`（1080p 30p 的资源，图像 1024×682），否则回到原厂逻辑。

QEMU（原厂 C3.11 + 同一补丁，`stock-liveplan.main`）：
- `LIV_9005`（1024×682）：帧缓冲注册成功（步长 1024），解码出第 1 帧，停在未建模的显示寄存器 `0x15421104`——与原厂尺寸的 LIV_9007 停在同一处。
- 4K 对照片：正常播放 13 帧。
- 走过的弯路：先用片段信息 `0xa0319f270` 做判断，适配器那次调用时它还没填，没命中；照着带 NFP 的镜像反汇编，把复制函数写成了 `0x40a10000`，在原厂固件上崩溃。

测试固件：`delivery/Z8-v44p-LivePlay1024-…-02e84221`（= 相机现用的 v44 02c37c4a + 该补丁 + 构建号重戳，MAIN 02e84221，Z_8_0406.bin 9f4995c5）。包本身未做 QEMU 回归。

## 真机 LIV_9007：首帧后卡住 → 音频要按 GOP 切块（2026-11-13 夜）

真机（v44）播放 LIV_9007：画面切到片段真实首帧，然后卡住、存储卡灯常亮，过一阵退回回放界面。

原因：播放分两段——先建解码器解 1 帧做首帧预览、关闭，再正式开始。正式开始时读取任务（`0x40344f00…`）按块号成对读视频块和音频块，`0x40ce7188` 取音频块 N 的字节数，要求不超过读取缓冲容量，否则回复状态 1 → MOVS 报 0x400 → 退出重试。Live 把整段音频（3.4 s，649 KB）写成一个块，超限。原厂对照片的音频块是 115 KB。

修正：`audio_chunks.py` 把音频按视频 GOP 的时间边界切成同样数量的块（只改音频 stsc/stco，PCM 数据不动；最大块 112 KB）。

QEMU 验证（为了用上完整建模的 4K 显示路径，把同一段画面做成 3840×2160 套进同一容器）：
- `LIV_9008`（4K，音频单块）：重现真机现象，只解 1 帧。
- `LIV_9009`（4K，音频切块）：**整段播完，95 帧全部解码**，回放界面进度条正常走（`qemu-run-9009-sheet.jpg`）。途中有一处音频输出寄存器 `0x1b802108` 模型没实现（16 位 sowt 音频，对照片是 24 位 lpcm），用 `Z8_TOLERATE=1b802000:1b803000` 越过；声音本身 QEMU 验证不了。

模型本地改动新增：`Z8_TOLERATE=lo:hi[,…]` 把指定范围的未建模访问变成记录后忽略。

## 真机 LIV_0002：整段播放成功，声音是噪声 → 音频要用原厂 lpcm 24 位（2026-11-13 夜）

真机（1080p 版，音频切块后）：**视频整段播放**，画面正确；声音刺耳、像噪声、重复。

原因：原厂音频是 `lpcm`（声音描述 v2）48 kHz 立体声 **24 位小端打包，6 字节/帧**；Live 写的是 `sowt` 16 位（v0 描述，4 字节/帧）。解析器接受 `sowt`，但播放链路只为 24 位准备：QEMU 日志里，24 位时固件给音频协处理器下 `Z8_LPCM_JOB command=3`（输入 N×6 字节 → 输出 N×8 字节，即 24→32 位转换）；16 位时这个任务不出现，数据未经转换直接送出。

修正：`audio_lpcm24.py` 把音频改成与原厂逐字节相同的 72 字节 `lpcm` 描述，样本左移 8 位成 24 位（mdat 音频段 ×1.5，音频 stco/stsz 相应更新）。

音频块容量：读取请求里缓冲容量是 0x2F000 = 192512 字节（24 位下 ≤ 32085 帧 ≈ 0.668 s）。15 帧 GOP 在 ≥22.5 fps 时满足；现片段最大块 168174 字节。

QEMU（4K 同容器，`LIV_9012`）：转换任务出现且参数正确（如 144150 → 192200 字节）。播放中仍会写未建模的 `0x1b802108`（与 16/24 位无关，对照片只有 0.4 s 单块所以没触发）。

## 真机 LIV_0003 沙漏 → 音频每块必须 ≤ 24024 帧；补丁支持任意非原厂尺寸（2026-11-13 深夜）

**音频块上限。** 0003（按 GOP 切块 + 24 位）真机沙漏，而 0002（同样切块、16 位）能播。原因：24 位要转成 32 位，输出缓冲 0x2F000 = 192512 字节 = 24064 帧；原厂每块正好 24024 帧（0.5005 s，输入 144144 → 输出 192192）。按 GOP 切的块最长 28029 帧，溢出。QEMU 佐证：块超过 24024 帧时固件写 `0x1b802108`（之前以为是模型缺口，其实是出错路径），且只下发第一个转换任务；改成固定 24024 帧一块（`audio_chunks.py IN OUT 24024`）后 7 个 `Z8_LPCM_JOB command=3` 全部下发、95 帧播完、不再碰 `0x1b802108`。音频块不需要和视频块一一对应。

**取景器 Live 是 1280×852。** 补丁改为通用（`win-lab ~/fxfix/liveplay/`）：
- `liveplan.S` v2（0x401fd000，196 B）：回放、HEVC、档位 0、界面层档位字 `0xa045f0908` == 9（尺寸不在原厂表）、宽 ≤1920、高 ≤1088 → 方案取 1080p 30p 资源，宽高取界面层文件信息。
- `livefbh.S`（0x401fd100，60 B，BL 自 `0x402f3c54`）：适配器把高度按 16 对齐（852→864），而 8 对齐编码的码流解码器报告 856，`0x40c347fc` 要求相等。若解码器报告值（实例表 `0xa02d30164 + id*32 + 8`）比对齐值小 ≤8，用报告值。
- QEMU（原厂 + 两段补丁，`stock-liveplan3.main`）：1024×682 与 1280×852（x265 测试流，编码高 856）都注册帧缓冲成功并解出首帧；4K 对照 13 帧正常。
- 真实取景器 Live 码流的编码高度（856 还是 864）尚未看到样本，两种都能过。
