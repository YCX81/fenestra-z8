# Z8 拍照档 Live 保存 1280×852

后续已用实际固件代码复演 ch2 软件登记、Y/UV 队列表和中断 mask 写入，并把 1280×852 的 90 帧 HEVC 有声测试流送入 Nikon 的 `hvcC` 提取器。ch1 槽容量新增了来自两组归档布局的定量结果。[后续调查与有声样片](HEVC-852-FLOW.md)

实拍的 `DSC_9776.MOV` 有 1024×682 行列的容器画幅，H.264 SPS 声明 1024×688，未设置裁剪。普通照片档已有 1280×852 的 **scaler 输入**读数。取得当次曝光的连续 1280×852 帧、把这 852 行如实写进码流，是需要分别闭合的两步。当前实拍样本和历史记录均未证实无 HDMI 时已保存这种文件。

本次离线输入为 `feat-mov/bg34.main`（基址 `0x40160000`，SHA-256 `c7c6dbeea8a94064a10d47a7b9022ab26e4aa6b12ba5fb63b1ad85abac4fe4d4`）及随附的 `src-fix31`。样片与项目顶层 `live-export/DSC_9776/DSC_9776.MOV` 逐字节相同，SHA-256 `31c0b8bdd196e85a87f833ed8f405ce648313a3a55f108a8e079355497077a5f`。这些是有版本的本地输入。当前机身运行的版本和显示几何尚未读回。

## 来自哪一级的 1280×852

| 环节 | 已有证据 | 尚需证明 |
|---|---|---|
| Scaler 输入 A0 | 既有 v16 真机记录，照片档 1280×852、4:2:2。录像档对应记录为 1920×1080。 | A0 的尺寸不足以描述 CMOS 实际读出、跳行方式或可供 CPU 取得的帧地址。 |
| 当前输出 ch1 | 照片档运行时记录 1024×682。启动配置 `lv_channel=1`，从输出几何、Y/UV 地址、各自 stride 转成同尺寸 I420，再送入 Wave5。 | 已保存的低分辨率文件无法恢复 scaler 缩小前的空间细节。 |
| 候选输出 ch2 | 无 HDMI 的历史观测中，原配置 1920×1080 NV16，没有观察到持续写帧。v17 改成 1280×852 NV12，寄存器值写入成功，缓冲仍未产出。 | v19-A/B 的 reset/kick 未有真机成功记录。原厂 `0x40cb87a0` 附近的单路重启样例选择 ch1、ch3 或 ch6，用在 ch2 属类推。尚缺 ch2 队列、完成事件及像素持续刷新的证据。 |
| 容器和预览 | `live_write_pair_aus()` 接收 stream 的宽高，写 `avc1/tkhd`。LVP 固定 1024×682，另走缩放和方向处理。 | MOV、机内 LVP、LCD/EVF 图层是三个尺寸系统，分别量测。 |

来源见[以往机身读数](../codex-w5/history/hw-notes.md)、[ch2 配置、快照和 IRQ 的反汇编](../codex-w5/history/astra-bjc3ml0to.md)、[采集器](src-fix31/capture/native_capture.c)、[连续帧转换和预览](src-fix31/capture/live_stream.c)与[保存调用](src-fix31/runtime.c)。

若继续验证 ch2，首先要在保持 ch1 负责 Live 的条件下，能对上多次不同画面的 ch2 Y **和** UV 内容、正确的 stride/有效范围、对应完成代次和前后快照。C0 的 A 组用 `s[5]/s[12]`。现有运行时 `picker=1` 的另组分支写死 `s[20]/s[27]`，选 ch2 时仍指向 ch1。默认 `picker=3` 则用已见的 Y 地址推测上一槽、套用当前 UV 距离，两者的判据不同。既有 16 项快照历史详细保存的是 ch1 字段，全通道的 `lv_snap[]` 只留最近一次 Y。两次 USB 读到同一个地址，或在 `ch2buf.py` 的两个 64 字节窗口看到非零，都不足以证明连续不撕裂的 852 行。ch1 若考虑加宽，要先查清每个原厂槽的容量、UV 起点及显示等消费者。此次只读显示参数的 USB 会话不包含切通道、开诊断采样或读 scaler MMIO。

## C 3.11 怎样处理 852 行

`open_stream()` 的 CONFIGURE 使用向上对齐 32 行的高度，另一路将实际宽高传入原厂 `PARAMS(0x402f6c10)`。我用 Unicorn 执行该参数函数的机器码和 `SET_PARAMS(0x40c338ac)` 的输入检查，运行至 `0x40c33d28` 停止，尚未取得服务锁，也未启动 VPU。输入与 Live 相同，AVC、8-bit、30000/1001、12 Mbps。[实际调用](src-fix31/codec/live_w5enc.c) · [可复跑脚本](evidence/check_w5_geometry.py)

| 输入 | CONFIGURE / 槽 Y 平面对齐高度 | PARAMS 描述宽高 | PARAMS +0x64/+0x68/+0x6c/+0x70 | 输入检查 |
|---|---:|---|---|---|
| 1024×682 | 704 | 1024×688 | 0, 0, 0, 0 | 通过 |
| 1280×852 | 864 | 1280×864 | 0, 0, 0, 0 | 通过 |
| 1920×1080 | 1088 | 1920×1088 | 0, 8, 0, 0 | 通过 |

`0x402f6c34..0x402f6c70` 将模式表高度按 16 向上取整，写入输出结构 `+8`。在 `0x402f6f48..0x402f6f68`，只有输入高度模 16 等于 8 时，`+0x68` 才写 8。不能期待这条分支自动给 852 补出 12 行裁剪。实拍 682 行的样本印证了无裁剪这一种情况。还没有从 **1280×852 真机 Wave5 HEADERS** 读出 SPS，不能把 864 行仿真参数当作已取得的码流。单独改 `+0x68` 的单位及整条下游映射也未经机身验证。

在当前实现中，VPU 槽只复制有效 Y 行和一半高度的色度行。若 VPU 处理对齐区，生产版本应当明确填充边缘 Y/UV、按完整覆盖范围做 cache clean，并从实际返回的 SPS 核对有效区域。对于该类逐行 4:2:0 AVC，若返回 1280×864、无已有裁剪，且已证实从第一行开始的 852 行有效，则期望的 SPS 裁剪为 `left=0,right=0,top=0,bottom=6`（12 个像素行）。容器 `avc1/tkhd` 用 1280×852，竖拍矩阵的平移用同一有效宽高。若 SPS 已正确裁剪，直接保留。

### 用现有 MOV writer 做的独立对照

在电脑上从 1280×852 测试图生成一帧 AVC，底部补至 864。用同一份压缩图像做两件 MOV，通过随附的 `live_mov.c` 写入。第二件只在 SPS 声明底部裁 12 行。测试没有运行 Wave5。FFmpeg 4.3.1 在两件 MOV 中都按容器解出 1,635,840 字节 I420；直接解裸 H.264 才把两件区分开。

| | MOV avc1/tkhd | SPS coded → display | 直接解裸码流输出 | 共同 1280×852 区域 |
|---|---|---|---:|---|
| 未裁剪 | 1280×852 | 1280×864 → 1280×864 | 1,658,880 B | 同一像素 SHA-256 |
| SPS 底裁 12 行 | 1280×852 | 1280×864 → 1280×852 | 1,635,840 B | 同一像素 SHA-256 |

这对夹具的视频 sample payload SHA-256 均为 `c082670b6ee4620ce2f93674f5b9c9e0f84a68076bb1279f92c43796355a30e7`，共同区域 I420 的 SHA-256 均为 `a699a9582ccad0d15d73fe2ddfd4458d33544a9c2fb68bb554a63b8572dd3ab0`。现有 writer 能写出一致的 852 行显示几何，条件是上游交给它的 SPS 正确。实拍样片 00 与容器改为 688 行的 07 也做了独立的整段解码对照。[实拍解码记录](tests/decoded.json)

两份 **真实含 1280×852 测试图**的夹具也分别送入该 MAIN 的 `0x40ce8a08`。以 Live writer 原格式输入，均返回 6。加入 `niko`、删除 `mebx` 后，均返回 0，查询 udta 返回 3。随后加入同一段模拟 donor 的 324,169 B udta，两件仍返回 0，udta 查询和读取均返回 0，内容检查返回 1、身份状态为 0。此处每件只有一帧视频且无音轨，输入由模拟文件读取回调提供；结论只覆盖该解析入口和提取函数。实拍有声的 06 与 09 则独立检验了仅增加 SPS 裁剪的效果。[原厂 parser 夹具](evidence/check_ncdt.py) · [有声样片矩阵](tests/MATRIX.md)

在本目录复跑以下命令。FFmpeg 需带有 `libopenh264` 和 `h264_metadata`，或将 `ffmpeg` 替换为本机该可执行文件的路径。产物仅写临时目录。

```sh
../feat-rec/.recorder-venv/bin/python evidence/check_w5_geometry.py
work=$(mktemp -d)
cc -std=c11 -O2 -I src-fix31/codec evidence/probe_852_mux.c src-fix31/codec/live_mov.c -o "$work/mux"
ffmpeg -v error -f lavfi -i 'testsrc2=size=1280x852:rate=30' -vf 'pad=1280:864:0:0' -frames:v 1 -c:v libopenh264 -b:v 4M -threads 1 -f h264 "$work/full.h264"
ffmpeg -v error -f h264 -i "$work/full.h264" -c:v copy -bsf:v h264_metadata=crop_bottom=12 -f h264 "$work/crop.h264"
for tag in full crop
do
  "$work/mux" "$work/$tag.MOV" < "$work/$tag.h264" || exit 1
  python3 -B mov_fix.py "$work/$tag.MOV" --inspect
  ffmpeg -v error -f h264 -i "$work/$tag.h264" -pix_fmt yuv420p -f rawvideo - | wc -c
  ffmpeg -v error -f h264 -i "$work/$tag.h264" -vf 'crop=1280:852:0:0' -pix_fmt yuv420p -f rawvideo - | shasum -a 256
done
```

同一临时目录的两件 MOV 可复跑上述原厂函数检查（需 pyelftools、clang 和 qemu-system-aarch64）。

```sh
../feat-rec/.recorder-venv/bin/python -B - "$work" <<'PY'
from pathlib import Path
import sys
sys.path.insert(0, "evidence")
import check_ncdt as native
from mov_fix import rewrite
native.checked_file(native.ROOT / "bg34.main", native.FIRMWARE_HASH)
donor = native.checked_file(native.DONOR, native.DONOR_HASH)
cases = []
for name in ("full", "crop"):
    original = (Path(sys.argv[1]) / (name + ".MOV")).read_bytes()
    cam = rewrite(original, niko=True, remove_mebx=True)
    with_meta = rewrite(cam, ncdt_donor=donor)
    cases.extend([(name, original, [6]), (name + "-cam", cam, [0, 3]),
                  (name + "-meta", with_meta, [0, 0, 324169, 0, 1, 0])])
native.replay([], cases)
PY
```

## 工作量与验收

- 紧凑 NV12/I420 每帧由 1,047,552 B 增至 1,635,840 B，增加 56.16%。30 fps 时，每次完整单向传输约 49.1 MB/s。链路有不止一次读写，取景 DMA、复制、编码和写卡要分别测。既有约 4 ms 的 1024 编码耗时无法保证目标尺寸的 30 fps。
- 此版本已为目标尺寸预留四个 VPU 槽，每槽 1,658,880 B，共 6,635,520 B。它没有为 ch1 的原厂 DMA 槽增容，也不会让 ch2 产帧。压缩 AU ring 与冻结区各 5 MiB，12 Mbps 理论上约容纳 3.50 秒。优先保留现有码率，待实拍再判断细节、码率峰值与 IDR 裕量。
- LVP 现在每次写 47,139,872 B（45 帧加文件头），50 槽加 scratch 共占 53,425,152 B RAM。删掉这条路径需要原厂播放的完整生命周期通过。尺寸测试与删 LVP 可以独立进行。[固件改动落点](firmware-plan.md)
- 真机 852 行的交付条件是同一段拍摄能对上稳定的源帧、编码器实际 SPS、容器有效区域，并可完整解码。需分别观察空闲/半按/快门窗口的独立帧数、PTS、重复与撕裂、底部 Y/UV 和竖拍旋转。原厂列表、缩略图、有声播放、返回照片以及 Apple 照片导入各有独立结果。

## 外部 04.23 对这条路线的帮助

本地克隆 HEAD 为 `ab631a8`（2026-11-04），文档对应 04.23，基础为 Z8 C 3.11。本次只读其代码、资源和发布记录。核对本机 MAIN 指令，ProRes 写出与解析入口 `0x40cee4d0`、`0x40ce9acc` 已分支到 `0x40a00180`、`0x40a001cc`，预拍入口 `0x40f6fe90` 已分支到 `0x409f0000`，图片查询 `0x4032dc64` 已分支到 `0x40a41090`。这些是该系列补丁痕迹，不能据此推定本机等同于整包 04.23。[版本记录](../../../external/NikonFirmwarePatch-04.18/docs/release-04.23.md) · [ProRes 原厂入口及补丁用途](../../../external/NikonFirmwarePatch-04.18/z8prores/back_half.py)

- 预拍模块把 pool `0x39` 用于 C15/C30 的压缩 RAW 历史，后续还要 Tdec 解码。普通照片档 Live 要的是可连续取得的 YUV。跨模式驻留、分配长度及 DMA 所有权仍需分别验证。[预拍缓冲实现](../../../external/NikonFirmwarePatch-04.18/z8precapture/firmware.c)
- ProRes 增加的是已有录像路径的档位和 FourCC 识别；H.265 Log 改的是已有 10-bit 路径的曲线与色彩。它们没有提供普通拍照档的 1280×852 DMA 源、still 界面启动任意 MOV 的 API，或 REC 前安全释放 Wave5 的实现。项目自己的旧 HEVC 客户端已有 QEMU 配对、封装证据，也记录了回放阻塞；它可作文件对照，仍需共享服务的交接。[Log 路径](../../../external/NikonFirmwarePatch-04.18/docs/experimental-h265-log3g10.md) · [旧客户端验证范围](../../../_mac-migration/files/_bundle-20261102/codex-tasks/w5-client/evidence/final-summary.json)
- 开放门撤销操作有实机显示先更新、传感器沿用旧状态的记录；QEMU 追到原厂比较器 `0x40f81010` 的字段相等导致跳过模式重配。像素位移的 I/O 线程超时后可请求取消，仍等 `completed` 才结束对已被领取作业的等待。这两处给出了等待哪一种完成信号的范例。[模式切换](../../../external/NikonFirmwarePatch-04.18/z8opengate/src/d8_hooks.S) · [I/O 所有权](../../../external/NikonFirmwarePatch-04.18/z8pixelshift/src/firmware.c)
- `Z8PRESTP.BIN` 是预拍 NEF 写入/查找/超时的 32 B 停止文件。外部 Log 文档中的 CAPTG 异常与转储属于特定 QEMU 配置。两者都没有给出这台机身 REC 约 27 秒重启的复位原因、故障 PC 或可靠的崩溃报告导出办法。现有机身实验支持完整交接后曾能录像，失败那次停在哪个阶段仍需独立观测。此次卡测和尺寸调查无需灯码固件；单独要区分 REC 的返回值与绑定阶段时，已有灯码仍是候选，缺码无法定位。[停止文件定义](../../../external/NikonFirmwarePatch-04.18/docs/stop-file.md) · [REC 复盘](../codex-w5/W5-MOVIE-HANDOFF.md)
