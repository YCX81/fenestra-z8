# C64 i 菜单编号：只读调查与离线原型

## 结论与范围

本次输入仅为 `bg34.main`（81,807,709 字节），基址 `0x40160000`，SHA-256 `c7c6dbeea8a94064a10d47a7b9022ab26e4aa6b12ba5fb63b1ad85abac4fe4d4`。未取得 v36 MAIN；这里的地址、空间和冲突结论只针对该 v31 文件，C64 层相同来自用户说明。没有连接 USB、访问相机、刷写、修改输入 MAIN、生成更新容器。

**不能把 i 菜单的两条路径混成一种编号资源：**

- 拨盘快速选择条：C1～C9 是包含编号的 **64×32 灰度 PNG**，有五种变体；C64 层把 C10～C64 的私有 ID 转成 ASCII 文字。目前没有这 275 个 ID 对应的 PNG。
- i→PC→OK 的 state2 示例图列表：示例图下方的 C1～C9 是 **ASCII `C-1`…`C-9`**，不是上述 PNG；示例图是另一个子控件。扩展层已经提供 `C-10`…`C-64` 字符串和解析器。声称“下方没有编号，因为缺 PNG”不符合这条路径的静态证据。
- state2 原厂字体样式为 `0x229`，扩展字符串统一使用 `0x21f`。样式的第二字节分别为 `0x1c` / `0x24`（28 / 36），原生文字布局的高度为 28，宽度为 62。这是具体的不一致，优先验证；**没有动态像素证据，不能把它定为真机空白的唯一原因**。缓存、裁切、初始化时序仍未排除。

已保存 [完整反汇编](evidence/disassembly.txt)、[数据表审计](evidence/static-audit.json)、[原图清单](prototype/original-resources.json)。文件偏移规则：常规 VA 减 `0x40160000`；原厂初始化 RAM `0xa02808000..0xa02ab5000` 来自 MAIN `0x4b13000..0x4dc0000`，不能直接减 MAIN 基址。

## 1. 拨盘选择条：图片编号

原厂 `0x404532cc: bl 0x4045341c`。当前入口已是 `b 0x40b14000`；该 wrapper 先执行原厂九槽构造，再追加有效扩展记录。另一个照片页面 `0x4048edd4` 也有 wrapper，不能把它当作视频的唯一入口。

原厂九槽主体 `0x40453544..0x40453610`：

- `0x40453568` 读取转换后记录的 `+0x110`，与 `0x800` 比较；`0x403f9e64` 返回值 bit0 决定普通/带星号。
- `0x40453578/598/5b0` 读下表中的 u16 图片 ID。
- `0x404535d0: bl 0x403f9880`，返回 `0x20` 时改用 FC 的第三张原厂表（本报告编号为 v1）。
- `0x404535c8/5f4` 写入重定位后的 LABELS；当前 LABELS=`0xa116c7000`，SELECTORS=`0xa116c7200`。
- `0x404a7a20` 检查图片列表类型，`0x404a7a28: ldrh w1,[x20,x26,lsl #1]`，`0x404a7a30: bl 0x403f645c` 提交编号资源。

| variant | 选择条件（静态） | C1…C9 图片 ID（步长 2） | u16 ID 表 RAM | 图片外观 |
|---|---|---|---|---|
| 0 | +0x110 ≤0x800，bit0=1，非 FC | 0x045a…0x046a | 0xa028b5dc6 | 普通图标+C编号 |
| 1 | `403f9880` 返回0x20，覆盖其它条件 | 0x1824…0x1834 | 0xa028b5dd8 | FC图标+C编号 |

| 3 | +0x110 ≤0x800，bit0=0，非 FC | 0x045b…0x046b | 0xa028b5e3a | 普通图标+C编号+星号 |

### C10～C64 在该路径的现状

`label_id(s,v)=0x7e00+(s-10)*5+v`，范围 **0x7e00..0x7f12**，共275项，与 bank 无关。照片/独立视频选择器分别为 `0x1000+s-1` / `0x2000+s-1`；显示编号相同，可以共用图片。

当前 `0x403f645c → 0x40b12000`：`0x40b12000..0c` 检查该范围，`0x40b12084..94` 把 widget kind 改成3（ASCII），然后调用 `0x40325d48`。另一种内容提交入口 `0x403f61ec → 0x40b12800` 对 kind1 的同一范围做相同转换。原厂 ID 保持原路径，并有扩展文字→原厂图片的清理分支。

文字解析 `0x4032e70c → 0x40b12400`，从 `0xa116d0200+index*32` 取 `{string_ptr,length,style}`，返回给原厂渲染器。字符串存放 `0xa116cf000+index*16`。对275条全部静态解包，字符串均正确，length=4，style=0x21f；五种 variant 的文字完全相同，没有 FC/星号图像差别。初始化数据由 `0x40b20000` 启动代码清零、复制，当前有效压缩段结束 `0x40b39460`。

所以代码意图是显示原生 `C-10` 文字，不是 C9 图片，也不是完全没有编号数据。若这些 ID 直接以 kind1 进入当前图片查询，未命中 `0x7000..7014` 后会落入原厂越界回退；`0x4032dc7c..88` 将 ID 清成0。这是静态分支结论，不是已发生的 UI 运行记录。

## 2. OK 后示例图下方：原厂文字

state2 原厂行数组 `0xa028de368`，44字节/行，custom行索引31..39的 word0 是 **0xab..0xb3**。文字表 `0x42afbd18..0x42afbda8` 的9项 `{u64 ID,u64 string_ptr}` 指向 `0x42b04868+4*(s-1)`，内容 `C-1`…`C-9`。

关键路径：

1. `0x404ad5bc: mov w27,#0x229`。
2. `0x404ad7f0` 读取行 word0（当前跳入 `0x40b15e00` 后重放）；原厂 ID 用 `0x42afbb28` 表匹配。
3. `0x404ad844` 取字符串；bit0为0则经 `0x404ad84c..868` 的格式串构造带星号文本。
4. `0x404ad86c..874` 以 `w1=行文字ID,w2=0x229` 调 `0x403f2920` 初始化原生动态字符串。
5. `0x404ada58..68` 直接把行 word0 写 widget+8、kind3 写 widget+0xc。**这里不经过 `0x403f645c`。**
6. `0x4032b83c..848` 将文字资源交给 `0x4032e70c`；当前扩展解析器接管范围内ID。

图像是独立子控件：行 +0x14 给图片 ID，`0x403a77f4` 读出，`0x403a783c` 写子控件内容。扩展 `0x40b151e4..0x40b1521c` 根据记录 +0x110 查询 `0x42afba28`，写相应示例图片ID；word0 则在 `0x40b151c0..d4` 写入上述 label_id。**这里是“示例图片＋独立文字”，不需要按每种示例照片×64再做大图片。**

扩展复制原厂最后一行的44字节结构模板，然后替换文字ID、选择键与示例图ID；模板复用不是借用C9图片。`0x40b15e00` 检测扩展ID后跳 `0x404ad8b4`，跳过原厂字符串初始化，依靠自己的字符串表。

四套布局中，文字矩形分别来自 `0x43f8f442 / 0x43f8f4aa / 0x43f8f502 / 0x43f8f56a`，全部为62×28；示例图矩形为102×76。例 `(93,354,155,382)` 的下方文字区域，高度28。这里只是原厂布局坐标，未换算面板比例。

`0x40695e3c` 指向 `0x43a0d540+style*16`；两条样式原始字节：

- 0x229 @0x43a0f7d0：`12 1c 02 64 00 00 00 00 ff 00 00 00 00 00 00 00`
- 0x21f @0x43a0f730：`12 24 02 64 00 00 00 00 ff 00 00 00 00 00 00 00`

`0x4032b878..88c` 把样式第二字节写入渲染记录 +0x14/+0x16。两者字形选择首字节相同，尺寸参数不同。扩展36相对原厂28/文字框高28不一致，属于可复现的静态问题；是否导致整个标签消失，需实际渲染验证。

## 3. 建议补丁：分两条线

### A. 优先验证用户所指的图下文字

先做只改变 state2 的最小离线候选：对 kind3、ID在0x7e00..0x7f12的 state2 label，用原厂样式0x229。最小诊断可以暂时把全部275条扩展文字描述符 style从0x21f改成0x229，并在QEMU比较；这会影响所有使用这些文字ID的页面，**只作为定位实验，不当作无副作用的最终实现**。

最终可把 state2 分离为55个私有文字ID（例如拟议 `0x7f20..0x7f56`，须另做全局文字ID冲突审计），在 `0x40b151c0..d4` 根据slot生成，`0x40b15e00` 同步范围检查，`0x40b12400` 增加解析器分支，明确使用0x229。其余拨盘/OSD可独立用图片。若需要星号，保留两种文字内容并按bit0选择；不能用55项静态字符串丢掉原厂修改状态。

先不要扩大字框：用原厂28号字体实测 `C-10`、`C-64`、带星号能否放入62宽；不够时依据字体实测宽度调整布局或间距。没有本次QEMU像素证据，不能预先承诺62宽足够。**给图片查询链注册PNG，并不会改变这条直接kind3的路径。**

### B. 给图片选择条恢复完整编号图标

已有 label_id 可直接用作图片私有 ID，无需另占 `0x1862+`：275张64×32、8位灰度PNG，5变体×55编号，两bank共用。这里的“基础样式”指编号图标的5种变体，不是所有示例照片。

1. 保留原厂图片表、21张现有私有图片以及已有模式映射。另设275项16字节表，结构 `{u32 0x100,u32 PNG_len,u64 ptr}`。
2. `0x40a4113c` 当前是 `mov x9,#0xcd58` 的回退入口，可跳到新的 C64 查询分支；命中后按原函数返回描述符，未命中重放指令并跳 `0x4032dc68`。不要直接覆盖 `0x4032dc64` 的已有分支。
3. **同时处理第二查询接口**：`0x4032dd34 → 0x40a41150`，其回退点 `0x40a411f4` 为 `mov x8,#0xcd58`；命中要通过x1/x2返回size/pointer，未命中跳 `0x4032dd38`。只改一个入口会留下尺寸/解码路径不一致。
4. 调整 `0x40b12000` / `0x40b12800` 对这些ID的kind转换：图片调用保持kind1，不再强改kind3，继续调用已有 `0x40325d48 → 0x40a41000` 映射链。不能删除文字resolver，它仍服务state2。需保留旧文字对象到图片的资源清理，以及原厂/扩展往返的kind恢复。
5. state2若坚持用PNG代替图下文字，需要额外改 `0x404ada58..68` 的kind及62×28文字框；64×32不适合原框。这是改变原厂页面设计，不是图片查表补丁自然带来的结果，故不作为首选。

### 放置与字节预算（拟议，未应用）

- 现有 `0x40a41400` 的21项表刚好在 `0x40a41550` 结束，下一字节就是51项模式重映射表。**禁止原地追加。**
- 新表拟放 `0x40b80000`：4400字节，结束0x40b81130。
- 新两个resolver拟放 `0x40b81200..0x40b82000`，预留3584字节（尚未编译，不能声称机器码已适配）。
- PNG池拟放 `0x40b82000..0x40bb9097`：PNG原始合计223354字节，16字节对齐后225431字节。
- 整个预留 `0x40b80000..0x40bc0000` 为256 KiB，本输入逐字节全零；使用至0x40bb9097，尚余0x6f69字节。
