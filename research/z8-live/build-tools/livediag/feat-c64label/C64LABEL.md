# C64 图下编号：样式定位与共享描述符补丁

本次只做本目录离线文件分析、补丁生成和静态验证；未连 USB、未访问相机、未刷写、未运行 QEMU。输入 `bg34.main` 为 81,807,709 字节，SHA256 `c7c6dbeea8a94064a10d47a7b9022ab26e4aa6b12ba5fb63b1ad85abac4fe4d4`，VA 基址 `0x40160000`。两张用户照片显示 state2 图下原厂文字存在、扩展文字空白；照片没有证明空白的唯一原因是字体尺寸。

**范围结论：可以证明只接管扩展 ID，不能证明只影响 state2 页面。** 原有代码本来就共享文字 resolver；本候选会同时把拨盘选择条和 OSD 中使用同组扩展 ID 的文字改为 28 号。工作中出现的 FIX2.md 已明确接受此范围；当前交付按该共享描述符方案对齐。若要求其他页面的扩展文字也完全不变，本候选不满足该要求，须另做 state2 私有 ID/描述符分流。没有为了“页面隔离”去改全局样式 0x21f，也没有添加未审计的分流代码。

## 1. 0x21f 的确切位置和路径

来源源码只读核对：`/path/to/Nikon/_mac-migration/files/_bundle-20261102/slotcode/tools/z8_slots_labels.py`：

- 第 16 行 `DEFAULT_STYLE_ID = 0x21F`。
- 第 39 行将默认值展开为全部条目；第 41–44 行将 `{u64 ptr,u32 length,u32 style,u32 reserved}` 写入 32 字节步长的描述符。
- MAIN 中没有一条给所有标签初始化为 `0x21f` 的立即数指令；这里是静态数据，启动时复制到 RAM。

定义 `j=(slot-10)*5+variant`，slot=10..64，variant=0..4，j=0..274：

| 项目 | 确切地址/内容 |
|---|---|
| 资源 ID | `0x7e00+j`，含端点上界 `0x7f12` |
| RAM 字符串 | `0xa116cf000+j*16`，ASCII `C-10`…`C-64`，length=4 |
| RAM 描述符 | `0xa116d0200+j*32` |
| RAM 样式字段 | 描述符 `+0xc`，`1f 02 00 00` |
| MAIN 描述符源 | `0x40b37208+j*32` |
| MAIN 样式字段 VA | **`0x40b37214+j*32`**；最后 `0x40b39454` |
| MAIN 样式文件偏移 | **`0x9d7214+j*32`**；最后 `0x9d9454` |

第一条完整头部原字节：

```text
40b37208: 00 f0 6c 11 0a 00 00 00 04 00 00 00 1f 02 00 00
           ptr = 0xa116cf000       length = 4 style = 0x21f
```

启动稀疏复制段 `{RAM-relative=0xa5200, size=0x2250, source=0x40b37208}` 包含全部 275 个描述符。`0x40b20058..c4` 清零/复制代码从 `0x40b20200` 取 `{offset,size}`，从 `0x40b20608` 顺序取有效载荷。它是去零段的稀疏打包，不是字节压缩，不能把 RAM 地址直接减 MAIN 基址。全部字段地址已列入当前 changed JSON 的 `byte_changes`。

关键反汇编（原始字节见 `evidence/c64label-disassembly.txt`）：

```text
40b12400  ldr w8,[x0]              // resource ID
40b12404  mov w9,#0x7e00
40b12408  sub w8,w8,w9
40b1240c  cmp w8,#0x112
40b12410  b.hi 0x40b1245c          // unsigned: 低于7e00也回退
...       x9 = 0xa116d0200
40b12424  add x9,x9,x8,lsl #5
40b12428  ldr w10,[x9,#0xc]        // 样式唯一读取点
40b1242c  cmp w10,#0x652
...
40b12444  str w10,[x3]             // 输出样式
40b12448  ret
40b1245c  mov x8,#0xac00
40b12460  b 0x4032e710             // 原厂 resolver 续点
```

原厂 C1..C9 state2 ID `0xab..0xb3` 不在接管范围，保持原厂路径：`0x404ad5bc: mov w27,#0x229`，`0x404ad86c..874` 用原厂字符串 ID 和 w27 调 `0x403f2920`。其他原厂文字 ID 同样回退；没有改这些指令或字体表。

扩展 state2：`0x40b151c0..d4` 按 `(slot-10)*5+variant+0x7e00` 写行 word0。`0x40b15e00..20` 仅对扩展范围跳到 `0x404ad8b4`，跳过原厂动态字符串初始化。它依赖上述静态描述符。`0x4032b848` 调 resolver 后，`0x4032b878..88c` 将 style 表的尺寸字节填入渲染记录的两个尺寸字段。

但 `0x403f645c→0x40b12000` 也将拨盘选择条的同组 ID 转成 kind3；`0x403f61ec→0x40b12800` 对 OSD kind1 同样处理。resolver 没有页面参数或 state2 判断。这是对“其他页面不受影响”的直接反例，不能以“只接管扩展 ID”冒充页面隔离。

样式表 `0x43a0d540+style*16`：

```text
0x21f @43a0f730: 12 24 02 64 00 00 00 00 ff 00 00 00 00 00 00 00
0x229 @43a0f7d0: 12 1c 02 64 00 00 00 00 ff 00 00 00 00 00 00 00
```

二者仅尺寸字节不同：36 → 28，face 为同一 0x12。布局的 62×28 不改。

## 2. 当前补丁与共存边界

工作期间，同目录并行流程按 `FIX2.md` 更新了 `c64label_patch.py`、`verify_c64label.py` 并生成 `bg34.c64label28.main`。本轮保留这些修改，独立重新运行当前 patch 函数并逐字节核对产物。

**当前交付直接改全部275条描述符的样式字段，不改指令：**

```text
j = 0..274
VA   0x40b37214 + j*32
file 0x009d7214 + j*32
每条原样式 1f 02 00 00 → 29 02 00 00
每条实际只改最低一个字节 1f → 29
```

共 **275 字节、275 个不连续的单字节范围**，首地址 `0x40b37214`，末地址 `0x40b39454`。全部地址/旧值/新值见 `bg34.c64label28.main.changed.json` 的 `byte_changes` 与 `changed`。

```sh
python3 -B c64label_patch.py bg34.main OUTPUT.main --json OUTPUT.changed.json
```

OUTPUT 必须为新路径。脚本核对固定 bg34 SHA、输入长度、boot copy代码/映射、全部目标描述符完整16字节及字符串；不匹配就拒绝。原文件和输出不得同路径，不覆盖已有输出。可接受其他区域不同的同布局 MAIN，并保留那些字节；这不是对任意另一版本的运行兼容认证。

当前产物：`bg34.c64label28.main`，81,807,709字节。

SHA256：`69f186822c9ab1b58597039e7f4898962b7e653bd95f5f716a51da23e197996b`。

共存依据是全文件差异严格等于上述275个地址：bootguard `0x401fe000` 段及 `0x401c4d4c` 等补丁点、Live `0x401e2000..0x401fff80`、NFP `0x40a41000..` 全部原样保留；没有新代码/空间分配，也没有改字符串、PNG、文字框或复制范围。已核对目标错误、重复打补丁、尾部截断均拒绝；保护区细节与散列见 JSON 的 `protected`。`verify_c64label.py` 为当前描述符方案的验证脚本。

字节无覆盖不等于界面无回归：其他页面使用共享扩展文字的尺寸也变为28，需回归拨盘选择条/OSD。

**旧实验产物区别：** 本轮较早曾生成 `c64label-229.main` 和对应 changed JSON，它仅在 resolver 将 `ldr w10,[x9,#12]` 改成 `mov w10,#0x229`（3个实际改变字节，SHA `2535e996f299c59226b55d0c8e794d3e9d522b9501eb07a1d9b75f84ff8ef27f`）。它不是当前脚本的输出，保留但不要与当前描述符方案混用/叠加。`evidence/c64label-disassembly.txt` 若包含 PATCHED resolver 尾段，该段同样仅对应旧实验；基线反汇编仍可用于定位。

## 3. 62 宽的字宽评估

**没有找到并确认 face 0x12 的原厂 advance/字形宽度表，不能给出字体引擎的精确像素宽度。** 检索 MAIN 的 `cmap/hmtx/OTTO/FreeType` 等未发现可直接解析的对应字体；单独出现的 `FNT` 字节位于不明二进制块，不能当成字体表证据。没有拿 PNG 编号字形或宿主字体冒充 state2 原生字体。

可复现的替代估算来自 `img_5008.jpg` 中已知原厂 28 号 C-5..C-8。照片 EXIF orientation=3，测量前仅在内存做方向归一化，原照片未改。测量方法为亮度阈值 min(R,G,B)>210、每列至少3像素；测量区域依次为 (245,465,322,502)、(391,470,465,510)、(535,472,615,512)、(684,474,766,514)，均为方向归一后的照片坐标：

| 标签 | 照片可见 ink 宽 | C→连字符、连字符→数字左边缘间距 |
|---|---:|---|
| C-5 | 54 px | 19、20 px |
| C-6 | 55 px | 19、20 px |
| C-7 | 57 px | 20、20 px |
| C-8 | 59 px | 21、21 px |

这些是照片像素，**不是布局坐标或字体 advance**。同位置示例图的宽约 126..138 照片像素；若以 MAIN 中示例图布局宽 102 作标尺，局部比例约 1.24..1.35。取较宽的估计区间，单字符节距约 14..17 布局单位；3 字符约 42..51，4 字符约 **56..68**，5 字符约 **70..85**。拍摄透视、图像控件内边距、抗锯齿和 bearing 都使这个换算不够精确，数字 0 的 advance 也没有实测；这只能用于判断风险，不是“每个数字等宽”的证明。

因此：

- `C-10`…`C-64` 都是 4 字符，宽度区间跨过 62，**存在临界或超宽风险，不能保证改成 28 就完整显示**。尤其需看 C-10/11/19/20/32/63/64、选中和未选中两态；不能因 C-11 看似窄就放过其他编号。
- 原厂星号格式在 `0x42af0727` 是 `%s*\0`。假设未来显示 `C-10*`，5 字符明显更危险；星号实际 advance 还未证实，不能给出确定溢出像素数。
- 当前 275 条字符串的五种 variant 全部是 4 字符 `C-xx`，**没有星号**；state2 扩展又绕开原厂 `%s*` 构造。这是现有行为，本补丁不会恢复修改标记，不能用“没有看到星号”判断宽度足够。

仅列备选，均未实施：优先对 state2 分流后去掉连字符（`C10`/`C10*`），分别减少为3/4字符；或验证同 face 更小尺寸/字距以保留完整文字；或把星号作为独立标记。去连字符后的带星号仍是4字符，仍须量宽。扩大文字框、添加 PNG 均未做。

最终判定要用 QEMU 同一布局的原生渲染测量/截图：resolver 输出 style=0x229 是必要观测，但不等于出现完整文字；如果仍空白或被截断，要区分宽度、缓存、初始化和 kind 路径，不据此直接扩框。
